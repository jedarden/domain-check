# Repository Health Best Practices

This document outlines best practices for maintaining a healthy git repository and preventing repository bloat.

## Overview

Repository bloat can occur gradually through:
- Large file commits (binaries, datasets, build artifacts)
- Accumulation of loose objects over time
- Inefficient garbage collection settings
- Lack of regular maintenance

Domain Check includes automated safeguards and monitoring to prevent these issues.

## Automated Safeguards

### Pre-commit Hook

A pre-commit hook (`.githooks/pre-commit`) automatically blocks commits that would add large files:

- **Maximum file size**: 50MB per file
- **Repository size warning**: Warns if repository exceeds 500MB
- **Action**: Blocks commit and suggests alternatives (Git LFS, .gitignore, etc.)

### Git Configuration

Automatic garbage collection is configured via `make setup-repo-health`:

```bash
# Runs auto GC when loose objects exceed threshold
git config --local gc.auto 256

# Limits packs generated by auto GC
git config --local gc.autoPackLimit 10

# Better compression for aggressive GC
git config --local gc.aggressiveDepth 50

# Prune loose objects after 2 weeks
git config --local gc.pruneExpire "2.weeks.ago"

# Keep reflogs for 90 days
git config --local gc.reflogExpire "90 days"

# Keep unreachable reflogs for 30 days
git config --local gc.reflogExpireUnreachable "30 days"
```

## Repository Health Scripts

### check-repo-size.sh

Quick repository size check with thresholds:
- **Warning**: 2GB
- **Critical**: 5GB

```bash
./scripts/check-repo-size.sh
```

### check-repo-health.sh

Comprehensive health diagnostics:
- Repository size check
- Large files in git history
- Git object count
- Large binary files in working directory
- Repository fragmentation analysis
- Git configuration verification

```bash
./scripts/check-repo-health.sh
```

### cleanup-bloat.sh

Crash-safe, memory-bounded bloat cleanup (replaces the bare
`git gc --aggressive --prune=now` that caused the 2026-08-12/14 memcg-OOM
crashes — see `docs/crashes/bf-173o7e-cleanup-verification.md`):
- Pre-flight gate aborts before any mutation on low disk, low memory, high
  load, a stale concurrent-gc lock, or a failed memory-bounded integrity check
- Every git stage runs under a hard systemd `MemoryMax` scope plus an
  RSS-sampling guard that kills the process group at the cap before the
  kernel's OOM killer can
- Staged execution with checkpoint/resume, progress heartbeat, and verbose
  logging to `.git/cleanup-bloat.log`

```bash
./scripts/cleanup-bloat.sh --check-only   # report needed/not-needed, change nothing
./scripts/cleanup-bloat.sh --dry-run      # print the staged plan, change nothing
./scripts/cleanup-bloat.sh                # run the bounded cleanup
```

### setup-git-gc-config.sh

Configures git automatic garbage collection settings. Run this once after cloning:

```bash
./scripts/setup-git-gc-config.sh
```

## Preventing Repository Bloat

### What NOT to Commit

- **Build artifacts**: `target/`, `dist/`, `node_modules/`, `.git`
- **Large datasets**: Files >10MB should use alternative storage
- **Binary files**: Images, videos, compiled binaries
- **Secrets/credentials**: API keys, passwords, certificates
- **Temporary files**: Logs, cache files, editor backups

### Alternative Storage Solutions

#### Git LFS for Binary Files

```bash
# Install Git LFS
git lfs install

# Track large files
git lfs track "*.bin"
git lfs track "*.tar.gz"
git lfs track "data/*.csv"

# Commit the .gitattributes file
git add .gitattributes
```

#### External Storage

- **Datasets**: Store in cloud storage (S3, GCS, Azure Blob) with download scripts
- **Build artifacts**: Use artifact registries (Docker Hub, npm, Maven Central)
- **Large media files**: CDN or media hosting services

#### Data File Splitting

Instead of one large dataset:
```
data/
├── small-sample.csv      # < 10MB, commit this
├── medium-dataset.csv    # 10-50MB, consider external storage
└── large-dataset.csv    # > 50MB, use external storage
```

## Monitoring Repository Health

### Health Indicators

**Healthy Repository:**
- Size: < 500MB
- Loose objects: < 1000
- Pack files: < 10
- No large files in recent history

**Warning Signs:**
- Size: 500MB - 2GB
- Frequent need for `git gc`
- Slower clone/pull times
- Large `.git` directory

**Critical Issues:**
- Size: > 2GB
- Hundreds of loose objects
- Many large files in history
- Clone takes > 5 minutes

### Regular Health Checks

Add to your development routine:
1. **Weekly**: Run `make check-health`
2. **Monthly**: Run `make check-health-full`
3. **Quarterly**: Run `./scripts/cleanup-bloat.sh` if needed

## Troubleshooting

### Repository is Too Large

**Symptoms:**
- Slow clone/pull times
- Disk space usage concerns
- CI/CD performance issues

**Solutions:**
1. Run health check: `make check-health-full`
2. Run cleanup: `./scripts/cleanup-bloat.sh`
3. Identify large files in history
4. Consider BFG Repo-Cleaner for removing large files from history

### Pre-commit Hook Issues

**If hook is not running:**
```bash
# Ensure hooks are executable
chmod +x .githooks/pre-commit

# Configure git to use local hooks
git config core.hooksPath .githooks
```

**If hook blocks legitimate files:**
- Use Git LFS for large files
- Add to `.gitignore`
- Split into smaller files
- Use external storage

### Frequent GC Needed

**If git gc runs too often:**
```bash
# Increase gc.auto threshold
git config --local gc.auto 512

# Or decrease it for more frequent cleanup
git config --local gc.auto 128
```
